JavaScript: Os Tipos de Erro

Na aula Lendo uma Mensagem de Erro, você viu que a linha mais importante da mensagem tem a forma Tipo: mensagem. A palavra antes dos dois-pontos (ReferenceError, TypeError, SyntaxError…) é o tipo do erro, e ela sozinha já diz muito sobre o que aconteceu. São poucos tipos, e cada um tem um "jeito" de aparecer. Conhecendo os principais, você bate o olho e já sabe onde procurar.

Você vai aprender
  • Os quatro tipos que você vai ver quase todo dia: SyntaxError, ReferenceError, TypeError e RangeError, com as mensagens reais mais comuns de cada um.
  • Os raros: URIError, EvalError e AggregateError.
  • Os erros que vêm do Node, como o ENOENT (arquivo não encontrado), que trazem informações extras.
  • Que todos são da mesma família, o Error, e como descobrir o tipo de um erro com name, message e instanceof.
  • O que não dá erro no JavaScript (e por isso engana): NaN, undefined, Infinity.

Todas as mensagens desta aula saíram do Node.js 24 da máquina da Ana (usuária ana, computador notebook). Para encurtar, as linhas at internas do Node (as que começam com node:internal) foram cortadas, com um aviso no lugar.

A ideia: a oficina mecânica

Quando o carro da Ana quebrou, o mecânico não disse só "está com defeito". Ele disse em qual parte: "é elétrico" (a bateria), "é no motor", "é pneu". Só com essa palavra a Ana já sabe mais ou menos o tamanho do problema e quem vai consertar.

1. SyntaxError: o código está mal escrito

É o erro de "gramática": um parêntese que não fecha, aspas sem par, uma chave sobrando. A aula Lendo uma Mensagem de Erro mostrou vários. O que eles têm em comum:

  • acontecem antes de o programa começar: nenhuma linha roda, nem as que estão certas;
  • as linhas at são todas do Node (wrapSafe…), porque o seu código nem chegou a rodar;
  • às vezes o número da linha aponta depois do erro de verdade.

O SyntaxError que acontece com o programa rodando: JSON.parse

Existe um caso em que o SyntaxError aparece no meio do programa: quando o próprio programa pede para ler um texto como código ou dados. O exemplo do dia a dia é o JSON.parse, que transforma um texto JSON em objeto. O seu programa está certo; quem está mal escrito é o texto:

const texto = "{nome: 'Ana'}";
const dados = JSON.parse(texto);

Repare: a primeira linha não é o seu arquivo, é <anonymous_script>:1 ("roteiro anônimo"), e a linha copiada é o texto que o JSON.parse recebeu. A mensagem diz "era esperado o nome de uma propriedade ou } no JSON, na posição 1": em JSON, os nomes têm de estar entre aspas duplas ({"nome": "Ana"}). A linha do seu código aparece no at: json.js:2.

2. ReferenceError: um nome que não existe

Você usou um nome (de variável, de função) que o JavaScript não conhece. Quase sempre é um erro de digitação:

const preco = 10;
console.log(preço);

$ node ref1.js
/home/ana/ref1.js:2

            ^

ReferenceError: preço is not defined
    at Object.<anonymous> (/home/ana/ref1.js:2:13)
«                                  (mais 7 linhas "at" internas, cortadas)

"preço não está definido". A variável se chama preco, sem cedilha; preço é outro nome. (É um dos motivos para escrever nomes sem acento: veja Nomes de Variáveis.) Outras causas comuns: maiúscula trocada (Nome × nome), variável criada dentro de um bloco { } e usada fora dele (veja Escopo).

let total = 0;

"Não é possível acessar total antes da inicialização". Desta vez o JavaScript sabe que total existe (ele leu o arquivo todo), mas a linha do let ainda não rodou. Uma variável let ou const só pode ser usada depois da linha que a cria (a aula Hoisting explica o porquê). Como consertar: crie a variável antes de usá-la.

3. TypeError: o valor não serve para isso

É o erro mais comum de todos. O nome existe, mas o valor que está nele não aceita o que você pediu. As mensagens mais frequentes:

Ler uma propriedade de null ou undefined 
const cliente = null;
console.log(cliente.nome);

$ node tipo1.js
/home/ana/tipo1.js:2
console.log(cliente.nome);
                    ^

TypeError: Cannot read properties of null (reading 'nome')
    at Object.<anonymous> (/home/ana/tipo1.js:2:21)
«                                  (mais 7 linhas "at" internas, cortadas)

Node.js v24.22.0

"Não dá para ler propriedades de null (lendo nome)". null e undefined são "nada": não têm propriedades. A versão com undefined (Cannot read properties of undefined) é ainda mais comum: aparece quando você pega uma posição que não existe num array, ou uma propriedade com o nome errado, e tenta ir mais fundo (turma[5].nome, cliente.compra.length).

Mudar uma propriedade de undefined 
let aluno;
aluno.nota = 10;

$ node tipo2.js
/home/ana/tipo2.js:2
aluno.nota = 10;
           ^

TypeError: Cannot set properties of undefined (setting 'nota')
    at Object.<anonymous> (/home/ana/tipo2.js:2:12)
«                                  (mais 7 linhas "at" internas, cortadas)

"Não dá para definir propriedades de undefined (definindo nota)". O let aluno; criou a variável sem valor (undefined), e não dá para pendurar uma nota no nada. Como consertar: let aluno = {};.

4. RangeError: fora da faixa

O valor é do tipo certo (um número), mas está fora dos limites que a operação aceita. Como um elevador que vai do térreo ao 10º andar: apertar "−1" ou "200" não faz sentido.

console.log(preco.toFixed(200));

5. Os raros: URIError, EvalError e AggregateError

O URIError aparece quando as funções que codificam e decodificam endereços da internet recebem um texto mal formado. O %, num endereço, tem de vir seguido de dois algarismos (%20 é o espaço):

console.log(decodeURIComponent("100%"));

$ node uri.js
/home/ana/uri.js:1
console.log(decodeURIComponent("100%"));
            ^

URIError: URI malformed
    at decodeURIComponent (<anonymous>)
    at Object.<anonymous> (/home/ana/uri.js:1:13)
«                                  (mais 7 linhas "at" internas, cortadas)

Node.js v24.22.0

"URI mal formada" (URI é o nome técnico de um endereço). Os outros dois:

  • EvalError existe por compatibilidade com versões muito antigas do JavaScript. Hoje o próprio JavaScript não o usa mais; você só o verá se alguém o criar de propósito.
  • AggregateError ("erro agregado") junta vários erros num só. Aparece com Promise.any, quando todas as tentativas falham (veja Várias Promises).

7. Todos são da mesma família: Error

Todos esses tipos são "parentes": cada um é um tipo especial de Error. Dentro do programa, um erro é um objeto, com duas propriedades principais:

  • name: o nome do tipo ("TypeError");
  • message: a mensagem ("Cannot read properties of null (reading 'nome')").

Para pegar o erro e olhar para ele, sem o programa parar, usa-se o try … catch ("tente … pegue"), que é o assunto da próxima aula. Uma espiada:

try {
  null.nome;
} catch (erro) {
  console.log(erro.name);
  console.log(erro.message);
  console.log(erro instanceof TypeError);
  console.log(erro instanceof Error);
  console.log(erro instanceof RangeError);
}

$ node nomes.js
TypeError
Cannot read properties of null (reading 'nome')
true
true
false

O instanceof ("é instância de", "é um") pergunta se o erro é de um tipo. Repare que ele é TypeError e também Error (todo TypeError é um Error, como todo gato é um animal), mas não é RangeError. Todos os tipos desta aula respondem true para instanceof Error:

const erros = [new Error("a"), new SyntaxError("b"), new ReferenceError("c"),
  new TypeError("d"), new RangeError("e"), new URIError("f"), new EvalError("g")];
for (const e of erros) {
  console.log(e.name, e instanceof Error);
}

$ node familia.js
Error true
SyntaxError true
ReferenceError true
TypeError true
RangeError true
URIError true
EvalError true

O new TypeError("d") cria um erro sem lançá-lo (é só um objeto; o programa segue). Na aula throw, você vai usar isso para criar os seus próprios erros.

Quando dá errado

Achar que a propriedade inexistente dá ReferenceError

O ReferenceError é só para nomes soltos (variáveis, funções). Para propriedades (o que vem depois do ponto), o JavaScript não reclama: obj.nmoe só devolve undefined, como você viu na seção 8. O erro só aparece se você for mais fundo (obj.nmoe.length), e aí é um TypeError apontando para o .length, não para o nome errado. Na mensagem Cannot read properties of undefined (reading 'length'), o culpado é o que vem antes do .length.

Pensar que o SyntaxError do JSON.parse é no seu código

A mensagem começa com <anonymous_script>:1, e não com o seu arquivo, e a linha copiada é o texto JSON. Quem tem que ser consertado é o texto (ou quem o produziu). A sua linha aparece no at, só para dizer de onde o JSON.parse foi chamado.

Procurar o erro na primeira linha quando ela é do Node

No ENOENT (seção 6), a primeira linha é node:fs:483, com um código do Node que você nunca escreveu. Não é bug do Node. Desça pelas linhas at até a primeira com /home/ana/: essa é a sua.

Resumo

  • A palavra antes dos dois-pontos é o tipo do erro, e ela já diz onde procurar.
  • SyntaxError: código mal escrito; nada roda. Também aparece com JSON.parse de texto mal formado.
  • ReferenceError: nome que não existe (digitação, acento, escopo) ou usado antes do let/const.
  • TypeError: o valor não serve para a operação; o campeão é Cannot read properties of undefined.
  • RangeError: número fora da faixa, ou recursão sem fim (Maximum call stack size exceeded).
  • Erros do Node (ENOENT…) são Error com um code e informações extras.
  • Todos são Error: têm name e message, e o instanceof diz o tipo.
  • NaN, undefined e Infinity não são erros: o programa segue, e o problema aparece mais adiante.
