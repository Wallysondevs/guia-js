JavaScript Estilo de Código

Um programa é lido muito mais vezes do que é escrito: por você mesma na semana que vem, por um colega, por quem vai consertar um defeito daqui a um ano. O computador não liga se o código está bonito ou feio; as pessoas ligam, e muito. Estilo de código é o conjunto de combinados que deixa o código fácil de ler: onde vão os espaços, como se dão nomes, quando usar ponto e vírgula. Nesta aula você vê os combinados que este guia segue desde a primeira aula, o porquê de cada um, e duas ferramentas que arrumam e conferem o código sozinhas.

Você vai aprender
  • Por que estilo importa, mesmo quando o programa "já funciona".
  • Indentação de 2 espaços e chaves { } sempre, com o defeito que a falta delas esconde.
  • Ponto e vírgula: o que o JavaScript faz quando você esquece, e as armadilhas reais disso.
  • Aspas, espaços, linhas em branco e comentários que explicam o porquê.
  • Como dar nomes: camelCase, PascalCase e MAIUSCULAS_COM_SUBLINHADO.
  • O Prettier (arruma a formatação) e o ESLint (aponta problemas), rodando de verdade.

Todos os programas e comandos desta aula rodaram no Node.js 24 da máquina da Ana (usuária ana, computador notebook).

1. Indentação: 2 espaços por nível

Indentar é empurrar uma linha para a direita para mostrar que ela está dentro de outra coisa: dentro da função, do if, do laço. Cada nível de "dentro" ganha mais 2 espaços:

function mostrarNotas(notas) {
  for (const nota of notas) {
    if (nota >= 7) {
      console.log(`${nota}: aprovada`);
    }
  }
}
function … {
Nível 0: encostado na margem.
for … {
Nível 1, dentro da função: 2 espaços.
if … {
Nível 2, dentro do laço: 4 espaços.
console.log(…)
Nível 3, dentro do if: 6 espaços.
} / } / }
Cada chave que fecha volta ao nível de quem ela fecha.

O JavaScript ignora a indentação (diferente do Python, onde ela é obrigatória). Ela existe só para as pessoas. Por que 2 espaços? É o combinado mais comum no JavaScript (o Prettier, que você vai ver abaixo, usa 2); 4 espaços também se vê. O importante é escolher um e usar sempre. Prefira espaços a tabulações (Tab): os editores de código, como o VS Code, já põem espaços quando você aperta Tab.

Chaves sempre, mesmo com uma linha só

O JavaScript deixa escrever um if sem chaves quando o bloco tem uma linha. Parece economia, mas a indentação pode mentir:

const estoque = 0;
if (estoque > 0)
  console.log("Tem pão!");
  console.log("Pode vender.");

$ node sem-chaves.js
Pode vender.

O estoque é 0 e o programa mandou vender! Sem chaves, só a primeira linha depois do if pertence a ele; a segunda roda sempre, apesar de estar indentada como se fosse do if. Com chaves, não tem como errar:

const estoque = 0;
if (estoque > 0) {
  console.log("Tem pão!");
  console.log("Pode vender.");
}

$ node com-chaves.js

(Nenhuma linha: com estoque 0, nada é mostrado, como deveria.)

2. Ponto e vírgula

O ponto e vírgula ; marca o fim de uma instrução. Se você esquece, o JavaScript tenta pôr um sozinho onde acha que falta. Isso se chama inserção automática de ponto e vírgula (em inglês, ASI). Quase sempre ele acerta; o bagunca.js lá de cima não tem nenhum ; e funcionou. O problema são as vezes em que ele erra.

Armadilha 1: o return sozinho na linha

function criarCliente(nome) {
  return
  {
    nome: nome
  };
}
console.log(criarCliente("Ana"));

$ node asi1.js
undefined

A função devolveu undefined, e não o objeto! Depois de um return seguido de quebra de linha, o JavaScript sempre põe um ;: para ele, a linha 2 é return; ("devolva nada"), e o objeto embaixo nunca é alcançado. Nenhum erro, nenhum aviso. Regra: o que vai ser devolvido começa na mesma linha do return: return {.

Armadilha 2: a linha que começa com [ ou (

const nome = "Ana"
[1, 2, 3].forEach((n) => console.log(n))

$ node asi2.js
/home/ana/asi2.js:2
[1, 2, 3].forEach((n) => console.log(n))
          ^

TypeError: Cannot read properties of undefined (reading 'forEach')
    at Object.<anonymous> (/home/ana/asi2.js:2:11)
    at Module._compile (node:internal/modules/cjs/loader:1929:14)  « linhas internas do Node cortadas
    …

Node.js v24.22.0

Aqui o JavaScript não pôs o ; no fim da linha 1, porque achou que a linha 2 continuava a 1. Ele leu as duas como uma só: "Ana"[1, 2, 3].forEach(…), isto é, "a letra da posição 3 de "Ana"", que não existe (undefined). Daí o erro: "não é possível ler propriedades de undefined (lendo forEach)", apontando para a linha 2. Com um ( no começo da linha acontece a mesma coisa: a linha de cima vira uma chamada de função, e sai TypeError: total is not a function (ou o nome que estiver lá).

O combinado deste guia: ponto e vírgula no fim de toda instrução. Assim você não depende de adivinhação. (Existem equipes que escrevem sem ; de propósito, num estilo chamado standard; elas conhecem essas armadilhas de cor. Para quem está começando, ; sempre é mais seguro.)

Missão: a função devolve undefined em vez da saudação. Conserte o return (o valor tem de começar na mesma linha dele) e rode até aparecer Bom dia, Ana!.

function saudacao(nome) {
  return
    `Bom dia, ${nome}!`;
}
console.log(saudacao("Ana"));

function saudacao(nome) {
  return `Bom dia, ${nome}!`;
}
console.log(saudacao("Ana"));

3. Aspas, espaços e linhas em branco

  • Aspas: o JavaScript aceita "pão" e 'pão', que são idênticos (veja Strings). Escolha um e use sempre; este guia usa aspas duplas. Quando o texto tem uma variável no meio, use a crase do template string: `Total: R$ ${total}` se lê melhor que "Total: R$ " + total.
  • Espaços em volta dos operadores: total = quantidade * preco, e não total=quantidade*preco. Depois da vírgula também: soma(1, 2).
  • Espaço antes da chave e depois do if/for/while: if (x) {, e não if(x){.
  • Linhas em branco separam "parágrafos": as constantes, cada função, o programa principal. Uma linha em branco, não cinco.
  • Linhas curtas: até uns 80 a 100 caracteres. Uma linha que não cabe na tela pode ser quebrada em várias.
  • Vírgula no último item de um objeto ou array em várias linhas (cidade: cidade,) é permitida e comum: acrescentar um item novo depois muda uma linha só.

4. Nomes

Um bom nome dispensa comentário. Compare let x = t * 1.1 com let precoComTaxa = preco * 1.1. As convenções do JavaScript:

O que éEstiloExemplos
Variáveis, constantes comuns, funções, métodoscamelCase: começa minúscula, cada palavra nova com maiúsculaprecoTotal, listaDeCompras, calcularDesconto()
ClassesPascalCase: toda palavra com maiúscula, inclusive a primeiraclass Produto, class ContaBancaria
Valores fixos "de configuração", conhecidos antes de o programa rodarMAIUSCULAS_COM_SUBLINHADOPRECO_PAO, MAX_TENTATIVAS

Evite nomes de uma letra (x, t), a não ser o i de um for curto ou o n de uma arrow function de uma linha. E, como combinado em Nomes de Variáveis, sem acento: preco, e não preço.

5. Comentários: o porquê, não o quê

Um comentário (veja Comentários) que repete o código só ocupa espaço. O comentário útil explica o que o código não consegue dizer: a razão de uma decisão, uma regra do negócio, um cuidado.

// Ruim: repete o que o código já diz
let tentativas = 0; // cria a variável tentativas com 0

// Bom: explica uma regra que não está no código
const MAX_TENTATIVAS = 3; // o banco bloqueia o cartão na 4ª senha errada

Se você precisa de um comentário para explicar o que um trecho faz, muitas vezes o melhor é dar um nome melhor ou separar o trecho numa função com um nome que diga isso.

6. As ferramentas: Prettier e ESLint

Ninguém precisa decorar regras de espaço. Existem programas que fazem isso:

  • Prettier ("mais bonito") é um formatador: reescreve o arquivo com espaços, quebras de linha, aspas e ; padronizados. Ele não muda o que o programa faz.
  • ESLint é um linter ("catador de fiapos"): lê o código e aponta problemas e maus hábitos (var, ==, variável criada e nunca usada…). Ele não roda o programa.

Os dois são pacotes do npm. A Ana criou uma pasta estilo, pôs o bagunca.js nela, criou o package.json com npm init -y e instalou os dois como ferramentas de desenvolvimento (--save-dev):

ESLint: apontar problemas

O ESLint precisa de um arquivo de configuração dizendo quais regras usar. A Ana criou o eslint.config.mjs na pasta:

import js from "@eslint/js";

export default [
  js.configs.recommended,
  {
    languageOptions: {
      globals: { console: "readonly", process: "readonly" },
    },
    rules: {
      "no-var": "error",
      "prefer-const": "error",
      eqeqeq: "error",
      camelcase: "warn",
    },
  },
];
js.configs.recommended
O pacote de regras recomendadas pelo próprio ESLint (variável não usada, variável que não existe, código que nunca roda…).
globals
Avisa que console e process existem sem precisar criar (são do Node).
rules
Regras a mais, cada uma com o nível: "error" (erro) ou "warn" (aviso). no-var: "sem var"; prefer-const: "prefira const"; eqeqeq: "use ==="; camelcase: "nomes em camelCase".

Não existe um estilo "certo" único: existem guias de estilo famosos (o do Airbnb, o do Google, o standard), e cada equipe escolhe o seu. O que importa é que todos no projeto sigam o mesmo. Os combinados do Guia JavaScript são estes:

Quando dá errado

A função devolve undefined sem motivo

Olhe o return: o valor começa na linha de baixo? A inserção automática pôs um ; logo depois do return (seção 2). Se o objeto da linha de baixo tiver duas propriedades (nome: nome, e cidade: cidade), o sintoma muda: o JavaScript lê as chaves soltas como um bloco de código, e o programa nem começa: SyntaxError: Unexpected token ':' ("símbolo inesperado :"), apontando para o cidade: cidade. Como consertar: comece o valor na mesma linha: return {, return (, return valor.

Cannot read properties of undefined ou … is not a function numa linha que começa com [ ou ( 
const total = 10
const texto = "Total: " + total
(function () { console.log("oi") })()

$ node asi3.js

"total não é uma função". O JavaScript juntou as linhas 2 e 3 e leu total(function …): como se você quisesse chamar o total passando a função da linha 3. O erro aponta a linha 2, mas a causa é o ; que faltou no fim dela. Como consertar: ponha ; no fim das linhas.

O if "não funciona": uma linha roda mesmo com a condição falsa

O if está sem chaves e a segunda linha só parece estar dentro dele (seção 1). Como consertar: chaves sempre.

Resumo

  • Estilo de código é para as pessoas: o computador roda os dois jeitos igual, mas só um é fácil de ler e de consertar.
  • Indentação de 2 espaços por nível e chaves em todo if/for/while, mesmo com uma linha só.
  • Ponto e vírgula sempre: a inserção automática erra no return sozinho na linha e nas linhas que começam com [ ou (.
  • Nomes: camelCase para variáveis e funções, PascalCase para classes, MAIUSCULAS_COM_SUBLINHADO para valores fixos; nomes que dizem o que a coisa é.
  • Comentários explicam o porquê.
  • O Prettier arruma a formatação (--check, --write); o ESLint aponta problemas como var, == e variável não usada (--fix conserta o que é seguro).
