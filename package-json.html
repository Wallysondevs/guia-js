JavaScript package.json

Na aula npm: Instalando Pacotes, o package.json apareceu como a "lista de compras" do projeto. Ele é mais do que isso: é a ficha do projeto, com o nome, a versão, os pacotes de que ele precisa, o jeito de rodá-lo e até se ele usa require ou import. É um arquivo de texto em JSON, que o npm e o próprio Node leem. Esta aula é só do Node.

Você vai aprender
  • Como criar o package.json: npm init com perguntas e npm init -y sem perguntas.
  • O que é cada campo: name, version, description, main, scripts, dependencies, devDependencies, type…
  • Como criar os seus atalhos de comando em "scripts" e rodá-los com npm start, npm test e npm run.
  • A diferença entre dependencies e devDependencies.
  • O que querem dizer ^4.18.1 e ~4.18.1.
  • Como o campo "type" decide entre require e import.
  • Os erros reais: Missing script, EJSONPARSE, require is not defined in ES module scope e Cannot use import statement outside a module.

Tudo rodou no Node.js v24.22.0 com o npm 11.19.1 da máquina da Ana (usuária ana, computador notebook).

A ideia: a ficha pregada na porta da cozinha

Na cozinha da padaria há uma ficha para cada receita: o nome, a versão ("pão de queijo, receita nº 3"), os ingredientes que precisam ser comprados, os utensílios que só a cozinha usa (a batedeira não vai para o cliente) e as instruções curtas ("para assar: forno a 180 °C por 25 min"). Qualquer funcionário novo lê a ficha e sabe o que fazer.

Na ficha da receitaNo package.json
Nome e número da receita"name" e "version"
Ingredientes para comprar"dependencies"
Utensílios só da cozinha"devDependencies"
"Para assar: forno a 180 °C""scripts": "start": "node index.js"

Sem perguntas: npm init -y

Com o -y (yes), o npm aceita tudo o que é padrão. É o mais usado: os campos se mudam depois. Repare como ele ajeita o nome quando a pasta tem letras maiúsculas e espaços:

$ mkdir "Padaria da Ana"
$ cd "Padaria da Ana"
$ npm init -y
Wrote to /home/ana/Padaria da Ana/package.json:

{
  "name": "padaria-da-ana",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC",
  "type": "commonjs"
}

O nome de um pacote é escrito em letras minúsculas, sem espaços (usa-se o hífen no lugar), por isso a pasta Padaria da Ana virou padaria-da-ana.

2. Os campos, um por um

Este é o package.json do cardápio no fim da aula, depois de a Ana instalar dois pacotes e criar alguns atalhos (você vai ver cada passo nas próximas seções):

$ cat package.json
{
  "name": "cardapio",
  "version": "1.0.0",
  "description": "Cardápio da padaria da Ana",
  "keywords": [
    "padaria",
    "pão"
  ],
  "license": "MIT",
  "author": "Ana",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1",
    "start": "node index.js",
    "ola": "echo Bom dia, padaria!",
    "formatar": "prettier --write feio.js"
  },
  "dependencies": {
    "lodash": "^4.18.1"
  },
  "devDependencies": {
    "prettier": "^3.9.10"
  },
  "type": "commonjs"
}
"name"
O nome do projeto (ou do pacote, se um dia for publicado). Minúsculas, sem espaços.
"version"
A versão, sempre com três números: 1.0.0. Veja o que cada um quer dizer na seção 5.
"description" e "keywords"
Descrição e palavras-chave: servem para as pessoas acharem o pacote no site do npm. Para um projeto só seu, são opcionais.
"license" e "author"
A licença e quem escreveu.
"main"
O arquivo principal: o que outro programa recebe ao fazer require("cardapio"), se o projeto virar um pacote. Para rodar o seu programa, quem manda é o "scripts".
"scripts"
Os atalhos de comando do projeto (seção 3).
"dependencies" e "devDependencies"
Os pacotes de que o projeto precisa para rodar e os que só servem para quem programa (seção 4). Quem escreve aqui é o npm install.
"type"
"commonjs" ou "module": diz ao Node como ler os arquivos .js (seção 6).

A ordem dos campos não importa: o npm às vezes a muda sozinho (o "type", aqui, foi parar no fim depois de a Ana mudá-lo e voltar atrás). O que importa é o JSON ser válido: aspas duplas nos nomes e nos textos, vírgula entre os campos e nenhuma vírgula depois do último.

O package.json é só JSON

Como é um arquivo JSON comum, o seu próprio programa pode lê-lo. Aqui, com o readFileSync do módulo node:fs (que tem aula própria: Lendo Arquivos) e o JSON.parse:

const { readFileSync } = require("node:fs");

const texto = readFileSync("package.json", "utf8");
const pacote = JSON.parse(texto);

console.log(`Projeto: ${pacote.name}, versão ${pacote.version}`);
console.log(`Descrição: ${pacote.description}`);
console.log("Dependências:", pacote.dependencies);

$ node ficha.js

3. "scripts": os atalhos do projeto

O campo "scripts" guarda comandos com apelidos. Em vez de lembrar e digitar o comando inteiro, você roda o apelido com o npm. O npm init já cria um, o test, que de propósito só avisa que não há testes e termina com erro:

$ npm test

> cardapio@1.0.0 test
> echo "Error: no test specified" && exit 1

Error: no test specified
$ echo $?
1
> cardapio@1.0.0 test
O npm avisa qual projeto (cardapio, versão 1.0.0) e qual script está rodando. (Esse > é do npm, não é o modo interativo do Node.)
> echo "Error: …" && exit 1
O comando que está no package.json. O npm o entrega ao terminal, como se você o tivesse digitado.
Error: no test specified
A saída do echo: "Erro: nenhum teste definido". É só um texto, não um erro do Node.
echo $? → 1
O código de saída foi 1 ("deu errado"), por causa do exit 1. Quando você tiver testes de verdade (aula Testes), troca esse comando.

Criando os seus: start e outros

A Ana escreveu o programa do cardápio, index.js:

const cardapio = ["pão francês", "sonho", "broa"];
console.log("Cardápio de hoje:");
for (const item of cardapio) {
  console.log(`- ${item}`);
}

Ela pode abrir o package.json num editor de texto e escrever os scripts à mão, ou pedir ao npm, com npm pkg set ("definir no pacote"), que não deixa o JSON estragar:

$ npm pkg set scripts.start="node index.js"
$ npm pkg set scripts.ola="echo Bom dia, padaria!"
$ cat package.json
{
  "name": "cardapio",
  "version": "1.0.0",
  "description": "Cardápio da padaria da Ana",
  "keywords": [
    "padaria",
    "pão"
  ],
  "license": "MIT",
  "author": "Ana",
  "type": "commonjs",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1",
    "start": "node index.js",
    "ola": "echo Bom dia, padaria!"
  }
}
$ npm start

> cardapio@1.0.0 start
> node index.js

Cardápio de hoje:
- pão francês
- sonho
- broa
$ npm run ola

> cardapio@1.0.0 ola
> echo Bom dia, padaria!

Bom dia, padaria!
npm start
Roda o script start ("começar"). É a convenção para "rodar o programa": quem pega um projeto desconhecido tenta npm start primeiro.
npm test
Roda o script test. O start e o test são especiais: dispensam o run.
npm run ola
"Rodar o ola": para qualquer outro nome, use npm run e o apelido.

E npm run sozinho lista todos os scripts do projeto:

$ npm run
Lifecycle scripts included in cardapio@1.0.0:
  test
    echo "Error: no test specified" && exit 1
  start
    node index.js
available via `npm run`:
  ola
    echo Bom dia, padaria!

"Lifecycle scripts" ("scripts do ciclo de vida") são os nomes especiais, como start e test; os outros estão "disponíveis via npm run".

4. dependencies × devDependencies

Alguns pacotes o programa usa para funcionar: são os ingredientes. Outros só ajudam quem programa: são os utensílios da cozinha. O prettier, por exemplo, arruma a formatação do código (espaços, ponto e vírgula); o programa em si não precisa dele. Para instalar um utensílio, use --save-dev (ou -D):

$ npm install lodash

added 1 package, and audited 2 packages in 469ms

found 0 vulnerabilities
$ npm install --save-dev prettier

added 1 package, and audited 3 packages in 479ms

1 package is looking for funding
  run `npm fund` for details

found 0 vulnerabilities

Os dois foram para a node_modules, mas para listas diferentes do package.json:

$ ls node_modules
lodash
prettier

  "dependencies": {
    "lodash": "^4.18.1"
  },
  "devDependencies": {
    "prettier": "^3.9.10"
  }

O aviso 1 package is looking for funding ("1 pacote procura financiamento") quer dizer que os autores do prettier aceitam doações; npm fund mostra o link. Não é erro. (Os tempos em ms e esse aviso mudam de uma instalação para outra.)

Um script que usa um pacote de desenvolvimento

Os scripts enxergam os programas dos pacotes instalados no projeto, sem npx. A Ana tem um arquivo bagunçado, feio.js:

const precos={sonho:3.5,broa:2,rosca:6}
  console.log( precos )

$ npm pkg set scripts.formatar="prettier --write feio.js"
$ npm run formatar

> cardapio@1.0.0 formatar
> prettier --write feio.js

feio.js 42ms
$ cat feio.js
const precos = { sonho: 3.5, broa: 2, rosca: 6 };
console.log(precos);

O prettier reescreveu o arquivo no estilo do guia: espaços em volta do = e das chaves, ponto e vírgula no fim, sem o recuo errado (o 42ms é o tempo que levou, e muda). O programa continua fazendo a mesma coisa; só ficou mais fácil de ler.

Por que separar?

Quando o projeto vai para um servidor, onde só precisa rodar, dá para instalar só os ingredientes com npm install --omit=dev ("omitir os de desenvolvimento"), economizando espaço e tempo. Na sua máquina, npm install instala as duas listas.

5. Os números da versão: ^ e ~

As versões seguem uma regra chamada versionamento semântico (semver): três números, PRINCIPAL.MENOR.CORREÇÃO.

ParteEm 4.18.1Sobe quando…
Principal (major)4O pacote muda de um jeito que pode quebrar quem usa (uma função some ou muda de nome)
Menor (minor)18Ganha coisas novas, sem quebrar nada
Correção (patch)1Só conserta defeitos

No package.json, o símbolo antes do número diz quais versões servem:

EscritoAceitaEm palavras
"^4.18.1"de 4.18.1 até antes de 5.0.0"Qualquer 4, a partir da 4.18.1". É o padrão do npm install.
"~4.18.1"de 4.18.1 até antes de 4.19.0"Só correções da 4.18"
"4.18.1"só a 4.18.1"Exatamente esta"

É por isso que, na aula npm, o npm update levou o lodash da 4.17.21 para a 4.18.1 (o ^4.17.21 permitia) mas nunca o levaria para uma 5. Para saber qual é a versão mais nova publicada de um pacote:

$ npm view lodash version
4.18.1

E para ler campos do seu próprio package.json pelo terminal:

$ npm pkg get name version
{
  "name": "cardapio",
  "version": "1.0.0"
}

6. "type": require ou import?

O JavaScript tem dois sistemas de módulos (veja Módulos (import e export) e require e module.exports). O campo "type" diz ao Node qual deles os arquivos .js do projeto usam:

"type"Os arquivos .js usamPara usar o outro sistema num arquivo
"commonjs" (o padrão do npm init)require e module.exportsDê a extensão .mjs ao arquivo
"module"import e exportDê a extensão .cjs ao arquivo

A Ana escreveu um arquivo com import num projeto "commonjs":

import _ from "lodash";

console.log(_.capitalize("bom dia!"));

E se não tiver "type"?

Sem o campo, o Node 24 trata o .js como CommonJS, mas, se encontrar import, tenta de novo como módulo e avisa. No lab, com o campo apagado (npm pkg delete type):

Quando dá errado

1. Missing script: esse atalho não existe

Antes de criar o start, a Ana tentou npm start:

$ npm start
npm error Missing script: "start"
npm error
npm error Did you mean one of these?
npm error   npm star # Mark your favorite packages
npm error   npm stars # View packages marked as favorites
npm error
npm error To see a list of scripts, run:
npm error   npm run
npm error A complete log of this run can be found in: /home/ana/.npm/_logs/2026-10-19T14_09_59_280Z-debug-0.log
Missing script: "start"
"Script faltando: start". Não há "start" no "scripts" do package.json.
Did you mean one of these? npm star…
"Você quis dizer um destes?". O npm achou parecidos dois comandos dele mesmo (star = "marcar com estrela" um pacote favorito). Não têm nada a ver com o seu projeto; pode ignorar.
To see a list of scripts, run: npm run
"Para ver a lista de scripts, rode npm run". É a melhor dica da mensagem.

Com um nome inventado, a mensagem é mais curta:

$ npm run abrir
npm error Missing script: "abrir"
npm error
npm error To see a list of scripts, run:
npm error   npm run
npm error A complete log of this run can be found in: /home/ana/.npm/_logs/2026-10-19T14_10_00_095Z-debug-0.log

Conserto: rode npm run para ver os nomes certos, ou crie o script. Confira também se você está na pasta do projeto.

2. EJSONPARSE: o package.json não é JSON válido

Editando à mão, a Ana deixou duas vírgulas depois de "MIT":

  "license": "MIT",,
  "author": "Ana",

$ npm start
npm error code EJSONPARSE
npm error JSON.parse Invalid package.json: JSONParseError: Expected double-quoted property name in JSON at position 158 (line 9 column 20) while parsing near "...\n  \"license\": \"MIT\",,\n  \"author\": \"Ana\",..."
npm error JSON.parse Failed to parse JSON data.
npm error JSON.parse Note: package.json must be actual JSON, not just JavaScript.
npm error A complete log of this run can be found in: /home/ana/.npm/_logs/2026-10-19T14_10_13_737Z-debug-0.log
code EJSONPARSE
"Erro ao analisar o JSON".
Expected double-quoted property name … (line 9 column 20)
"Esperava um nome de propriedade entre aspas duplas", na linha 9, coluna 20: logo depois da primeira vírgula, onde apareceu outra vírgula em vez de um nome. Vá direto a essa linha.
while parsing near "…\"MIT\",,…"
Um pedaço do arquivo em volta do problema (as \n e \" são a quebra de linha e as aspas, escritas do jeito do JSON).
package.json must be actual JSON, not just JavaScript
"O package.json tem de ser JSON de verdade, não só JavaScript". No JavaScript, uma vírgula sobrando no fim de uma lista é aceita; no JSON, não. Também não valem comentários (//) nem aspas simples.

O próprio node também se recusa a rodar um programa nessa pasta, porque ele lê o package.json para saber o "type":

3. Cannot use import statement outside a module

Foi o ola.js da seção 6, com import num projeto "commonjs":

(node:9) Warning: Failed to load the ES module…
Um aviso antes do erro: "Falhei ao carregar o módulo ES… defina "type": "module" no package.json mais próximo ou use a extensão .mjs". Já é a solução.
/home/ana/cardapio/ola.js:1 e o ^^^^^^
Linha 1 do seu arquivo, com o ^ embaixo da palavra import.
SyntaxError: Cannot use import statement outside a module
"Erro de sintaxe: não dá para usar import fora de um módulo". No modo CommonJS, import nem é uma instrução conhecida.

Conserto: "type": "module" no package.json, ou renomear o arquivo para ola.mjs, ou trocar o import por require.

4. require is not defined in ES module scope

O contrário: o velho.js da seção 6, com require, num projeto "module".

file:///home/ana/cardapio/velho.js:1
Linha 1 do arquivo. O file:// na frente é o jeito dos módulos ES de escrever um caminho (como um endereço).
ReferenceError: require is not defined in ES module scope, you can use import instead
"require não existe num módulo ES; você pode usar import".
This file is being treated as an ES module because…
"Este arquivo está sendo tratado como módulo ES porque tem a extensão .js e o package.json tem "type": "module". Para tratá-lo como CommonJS, renomeie para .cjs". O Node diz exatamente a causa e duas saídas.

Conserto: trocar const _ = require("lodash"); por import _ from "lodash";, ou renomear para velho.cjs, ou voltar o "type" para "commonjs".

Missão final: a lista de atalhos

Missão: faça um programa que mostre todos os scripts da aba package.json, um por linha, no formato npm run start → node index.js (dois espaços antes e depois da seta). Use Object.entries(pacote.scripts) num for … of (veja Percorrendo Objetos).

const { readFileSync } = require("node:fs");

const pacote = JSON.parse(readFileSync("package.json", "utf8"));

// mostre aqui cada script: npm run NOME  →  COMANDO

{
  "name": "cardapio",
  "version": "1.0.0",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1",
    "start": "node index.js",
    "ola": "echo Bom dia, padaria!",
    "formatar": "prettier --write feio.js"
  },
  "type": "commonjs"
}

const { readFileSync } = require("node:fs");

const pacote = JSON.parse(readFileSync("package.json", "utf8"));

for (const [nome, comando] of Object.entries(pacote.scripts)) {
  console.log(`npm run ${nome}  →  ${comando}`);
}

No lab, com o package.json do cardápio, a saída foi:

$ node comandos.js
npm run test  →  echo "Error: no test specified" && exit 1
npm run start  →  node index.js
npm run ola  →  echo Bom dia, padaria!
npm run formatar  →  prettier --write feio.js

Resumo

  • O package.json é a ficha do projeto, em JSON: nome, versão, scripts, dependências e tipo de módulo. npm init o cria com perguntas; npm init -y, sem.
  • "scripts" guarda atalhos: npm start e npm test rodam direto; os outros, com npm run nome; npm run sozinho lista todos.
  • "dependencies" são os pacotes para rodar (npm install x); "devDependencies", os só de quem programa (npm install -D x). Quem escreve essas listas é o npm.
  • Versões têm três números (principal.menor.correção). ^4.18.1 aceita qualquer 4 a partir da 4.18.1; ~4.18.1, só correções da 4.18.
  • "type": "commonjs" → require; "type": "module" → import. Misturar dá Cannot use import statement outside a module ou require is not defined in ES module scope.
  • O arquivo tem de ser JSON válido (sem vírgula sobrando, sem comentários, aspas duplas); se não for, vem o EJSONPARSE. O npm pkg set muda campos sem esse risco.
