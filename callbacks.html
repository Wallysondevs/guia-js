JavaScript Callbacks Assíncronos

Na aula Funções como Valores, você entregou funções ao forEach e ao map, que as chamavam na hora, uma vez por item. Nas aulas O que é Código Assíncrono e setTimeout e setInterval, você entregou funções que eram chamadas depois. Essas são os callbacks assíncronos: o jeito mais antigo de o JavaScript dizer "me avise quando terminar". Nesta aula você vai escrever as suas próprias funções com callback, aprender o combinado do Node para avisar erros, e conhecer o problema que fez o JavaScript inventar as Promises.

Você vai aprender
  • A diferença entre um callback que roda na hora e um que roda depois.
  • Como escrever uma função sua que recebe um callback e o chama quando termina.
  • O padrão do Node "erro primeiro": (erro, resultado) => { … }, e como tratar um arquivo que não existe.
  • Como seguir esse padrão nas suas funções.
  • O que acontece quando uma tarefa depende da outra: a pirâmide de callbacks.
  • Os erros reais: o erro ignorado, o callback chamado duas vezes, o callback que não foi passado.

Todos os programas desta aula rodaram no Node.js 24 da máquina da Ana (usuária ana, computador notebook), com node arquivo.js. Os arquivos de texto que eles leem estão mostrados com cat.

A ideia: deixar o telefone na padaria

Quando a Ana encomenda um bolo e diz "me liga quando estiver pronto", ela deixa o telefone com a padaria. A padaria não sabe nada sobre a vida da Ana; só sabe que, quando o bolo ficar pronto, tem de ligar para aquele número. E, se o forno quebrar, a padaria também liga, só que para dar a má notícia.

No código:

  • a padaria é a função que faz o trabalho demorado (ler um arquivo, esperar um tempo, buscar um preço);
  • o telefone é o callback, a função que você entrega;
  • a ligação é a padaria chamando o seu callback, com o resultado (ou com o erro).

1. Na hora × depois

Você já usa callbacks que rodam na hora:

const precos = [27.9, 5.49, 19.9];
precos.forEach((preco) => {
  console.log(`R$ ${preco.toFixed(2)}`);
});
console.log("Fim");

$ node sincrono.js
R$ 27.90
R$ 5.49
R$ 19.90
Fim

O forEach chama o callback três vezes e só então devolve o controle: o Fim vem por último. Esse é um callback síncrono. Agora uma função que avisa depois, escrita pela Ana:

function prepararPedido(item, quandoPronto) {
  console.log(`Preparando ${item}...`);
  setTimeout(() => {
    quandoPronto(`${item} pronto!`);
  }, 1000);
}

prepararPedido("pão de queijo", (aviso) => {
  console.log(aviso);
});
console.log("A atendente já foi atender outro cliente.");

$ node pedido.js
Preparando pão de queijo...
A atendente já foi atender outro cliente.
pão de queijo pronto!
function prepararPedido(item, quandoPronto)
Uma função comum com dois parâmetros. O segundo, quandoPronto, vai receber uma função: é o "telefone".
setTimeout(() => { … }, 1000)
Aqui o setTimeout faz o papel do trabalho demorado (na vida real seria o disco, a rede…).
quandoPronto(`${item} pronto!`)
A "ligação": quando o trabalho termina, a função chama o callback e entrega o resultado como argumento.
prepararPedido("pão de queijo", (aviso) => { … })
Quem usa a função entrega o callback: uma arrow que recebe o resultado em aviso e decide o que fazer com ele.
A ordem da saída
prepararPedido terminou na hora (depois de agendar o timer), o programa seguiu, e o aviso chegou 1 segundo depois.

Repare na divisão de tarefas: prepararPedido não sabe o que vai ser feito com o resultado (mostrar? guardar? mandar por e-mail?). Quem decide é o callback. É por isso que callbacks são tão úteis.

2. O padrão do Node: o erro vem primeiro

Trabalho demorado pode dar errado: o arquivo não existe, a internet caiu. Como avisar? O Node combinou um padrão que todas as funções com callback dele seguem: o callback recebe dois valores, e o primeiro é o erro.

  • Deu certo: o callback é chamado com erro valendo null e o resultado no segundo parâmetro.
  • Deu errado: o callback é chamado com um objeto de erro no primeiro parâmetro (e nada no segundo).

Isso se chama callback "erro primeiro" (em inglês, error-first callback). A Ana tem o cardapio.txt, mas não tem nenhum estoque.txt:

const fs = require("node:fs");

fs.readFile("cardapio.txt", "utf8", (erro, texto) => {
  if (erro) {
    console.log("Não deu para ler o cardápio:", erro.message);
    return;
  }
  console.log(`O cardápio tem ${texto.split("\n").length - 1} itens.`);
});

fs.readFile("estoque.txt", "utf8", (erro, texto) => {
  if (erro) {
    console.log("Não deu para ler o estoque:", erro.message);
    console.log("Código do erro:", erro.code);
    return;
  }
  console.log(texto);
});

$ node erro-primeiro.js
Não deu para ler o estoque: ENOENT: no such file or directory, open 'estoque.txt'
Código do erro: ENOENT
O cardápio tem 3 itens.
(erro, texto) => { … }
Os dois parâmetros do padrão: erro primeiro, resultado depois. Os nomes são escolha sua (err, dados…); a ordem é que é fixa.
if (erro) { … return; }
A primeira coisa dentro do callback é sempre conferir o erro. Se houver, trata e sai com return, para não continuar como se tivesse dado certo. Quando deu certo, erro é null, que é falso no if (aula Truthy e Falsy).
erro.message
A mensagem, em inglês: ENOENT: no such file or directory, open 'estoque.txt', "não existe esse arquivo ou pasta, ao abrir estoque.txt".
erro.code → ENOENT
Um código curto, bom para o programa testar: if (erro.code === "ENOENT"). ENOENT vem de "Error, NO ENTry" ("erro, não há essa entrada"): o arquivo não existe. Outro comum é EACCES: sem permissão.
A ordem da saída
O erro do estoque chegou antes do cardápio, mesmo tendo sido pedido depois: descobrir que um arquivo não existe é mais rápido que ler um. As duas leituras correram ao mesmo tempo, e cada callback foi chamado quando a sua terminou.

Missão: este programa tenta ler um estoque.txt que não existe e ignora o erro, então quebra com Cannot read properties of undefined (reading 'split'). Acrescente, no começo do callback, um if (erro) { … } que mostre Não achei o estoque e saia com return.

const fs = require("node:fs");

fs.readFile("estoque.txt", "utf8", (erro, texto) => {
  const linhas = texto.split("\n");
  console.log(linhas);
});

});

3. Seguindo o padrão nas suas funções

Quando você escreve uma função assíncrona com callback, siga o mesmo combinado: quem usar a sua função já sabe como tratar o resultado. A Ana faz uma função que "consulta" o preço de um produto (com um setTimeout fazendo o papel da demora de um sistema de verdade):

const tabela = { "pão francês": 0.8, "pão de queijo": 2.5, "café": 6 };

function buscarPreco(produto, callback) {
  setTimeout(() => {
    if (!(produto in tabela)) {
      callback(new Error(`produto desconhecido: ${produto}`));
      return;
    }
    callback(null, tabela[produto]);
  }, 500);
}

function mostrar(erro, preco) {
  if (erro) {
    console.log("Erro:", erro.message);
    return;
  }
  console.log(`Preço: R$ ${preco.toFixed(2)}`);
}

buscarPreco("café", mostrar);
buscarPreco("sorvete", mostrar);

$ node meu-erro-primeiro.js
Preço: R$ 6.00
Erro: produto desconhecido: sorvete
!(produto in tabela)
"O produto não é uma chave da tabela?" (o in pergunta se o objeto tem a propriedade).
callback(new Error(…)); return;
Deu errado: chama o callback com um objeto de erro (aula Lançando Erros) e sai. Em código assíncrono, em vez de throw, o erro é entregue ao callback (você vai ver por quê na seção Quando dá errado).
callback(null, tabela[produto])
Deu certo: null no lugar do erro ("nenhum erro") e o preço no segundo.
buscarPreco("café", mostrar)
O callback não precisa ser escrito na hora: pode ser uma função com nome, entregue sem parênteses. A mesma mostrar serve para as duas consultas.

4. Uma coisa depois da outra: a pirâmide

E quando uma tarefa assíncrona depende da anterior? A Ana quer: (1) ler o pedido de um arquivo, (2) calcular o total e salvar um recibo, (3) ler o recibo de volta para conferir. Cada passo só pode começar quando o anterior terminar, então cada um vai dentro do callback do anterior. O pedido:

$ cat pedido.txt
pão de queijo;4;2.50
café;2;6.00
bolo de cenoura;1;18.00

const fs = require("node:fs");

fs.readFile("pedido.txt", "utf8", (erro, texto) => {
  if (erro) {
    console.log("Erro ao ler o pedido:", erro.message);
    return;
  }
  const linhas = texto.trim().split("\n");
  let total = 0;
  for (const linha of linhas) {
    const [, quantidade, preco] = linha.split(";");
    total = total + Number(quantidade) * Number(preco);
  }
  const recibo = `Itens: ${linhas.length}\nTotal: R$ ${total.toFixed(2)}\n`;

  fs.writeFile("recibo.txt", recibo, (erro) => {
    if (erro) {
      console.log("Erro ao salvar o recibo:", erro.message);
      return;
    }

    fs.readFile("recibo.txt", "utf8", (erro, conferido) => {
      if (erro) {
        console.log("Erro ao conferir o recibo:", erro.message);
        return;
      }
      console.log("Recibo salvo:");
      console.log(conferido);
    });
  });
});

$ node piramide.js
Recibo salvo:
Itens: 3
Total: R$ 40.00

$ cat recibo.txt
Itens: 3
Total: R$ 40.00

Funciona (4 × 2,50 + 2 × 6,00 + 18,00 = 40), e o recibo.txt foi criado de verdade (o fs.writeFile é da aula Escrevendo Arquivos; o const [, quantidade, preco] pula o primeiro item, aula Desestruturação). Mas olhe o formato do código: cada passo empurra o próximo mais para a direita, e o fim do arquivo é uma escadinha de });. Com 5 ou 6 passos, vira uma pirâmide deitada, difícil de ler e de mexer. Os programadores apelidaram isso de callback hell ("inferno de callbacks") ou "pirâmide da desgraça".

Repare também que o tratamento de erro (if (erro) { … return; }) teve de ser repetido em cada nível. É esse o problema que as Promises resolvem: os passos ficam um embaixo do outro, e um só .catch trata o erro de qualquer passo.

Formas diferentes de fazer a mesma coisa

Quase toda função do Node que recebe callback tem uma irmã que devolve uma Promise, no módulo node:fs/promises (e, para funções de callback suas, existe o util.promisify, que faz a conversão). Compare a leitura do cardápio:

const fsp = require("node:fs/promises");

fsp.readFile("cardapio.txt", "utf8")
  .then((texto) => console.log(`O cardápio tem ${texto.split("\n").length - 1} itens.`))
  .catch((erro) => console.log("Não deu para ler:", erro.message));

$ node promisify.js
O cardápio tem 3 itens.

O resultado vai para o .then e o erro para o .catch, em vez dos dois chegarem juntos no mesmo callback. Os detalhes estão na próxima aula.

throw dentro de um callback assíncrono

Se a buscarPreco usasse throw new Error(…) em vez de callback(new Error(…)), o erro aconteceria dentro do setTimeout, quando quem chamou a função já foi embora: nenhum try … catch em volta da chamada o pegaria, e o programa inteiro pararia (você viu isso em O que é Código Assíncrono). É por isso que, com callbacks, o erro é entregue como primeiro argumento, e não lançado.

Resumo

  • Um callback assíncrono é uma função que você entrega para ser chamada depois, quando um trabalho demorado termina. A função que recebe o callback não espera: agenda o trabalho e devolve o controle.
  • O Node usa o padrão "erro primeiro": (erro, resultado) => { … }. Comece todo callback assim com if (erro) { …; return; }.
  • Nas suas funções, siga o mesmo combinado: callback(new Error(…)) + return quando dá errado; callback(null, resultado) quando dá certo; e chame o callback exatamente uma vez.
  • Em código assíncrono, os erros são entregues ao callback, não lançados com throw.
  • Passos em sequência viram callbacks dentro de callbacks: a pirâmide (callback hell). As Promises, a próxima aula, resolvem isso.
