JavaScript Assíncrono: o que é

Até agora, todo programa seu rodou como uma receita: linha 1, depois linha 2, depois linha 3, cada uma esperando a anterior terminar. Mas muita coisa num programa de verdade demora: esperar 2 segundos, ler um arquivo do disco, buscar dados na internet, esperar o clique de um botão. Se o programa ficasse parado esperando cada uma delas, ele passaria a maior parte do tempo sem fazer nada. O JavaScript resolve isso com o código assíncrono: começa uma tarefa demorada, segue em frente, e cuida do resultado quando ele chegar. Esta aula é a porta de entrada de todo o grupo "Assíncrono".

Você vai aprender
  • A diferença entre código síncrono (um depois do outro, esperando) e assíncrono (começa, segue, reage depois).
  • O primeiro setTimeout, e por que a ordem da saída não é a ordem do código.
  • Por que um laço pesado trava tudo, até um timer de 0 ms.
  • Ler um arquivo dos dois jeitos: readFileSync (esperando) e readFile (sem esperar).
  • Os três estilos de código assíncrono que você vai aprender nas próximas aulas: callbacks, Promises e async/await.
  • Os erros clássicos: o undefined de quem usou o resultado cedo demais, o Promise { <pending> } e o try que não pega o erro.

Todos os programas desta aula rodaram no Node.js 24 da máquina da Ana (usuária ana, computador notebook), com node arquivo.js.

A ideia: a encomenda de bolo

Imagine dois jeitos de comprar um bolo de aniversário na padaria do bairro:

  1. Jeito síncrono: a Ana pede o bolo e fica parada no balcão as duas horas que ele leva para ficar pronto. Não vai ao mercado, não busca o irmão na escola, não faz nada. Só depois de pegar o bolo ela segue o dia.
  2. Jeito assíncrono: a Ana pede o bolo, deixa o telefone e diz "me liga quando estiver pronto". Vai ao mercado, busca o irmão… Quando o telefone toca, ela volta e pega o bolo.

No segundo jeito, o bolo demora o mesmo tanto, mas a Ana aproveita o tempo. E repare numa coisa: a ordem em que as coisas terminam (mercado, irmão, bolo) não é a ordem em que ela as começou (bolo, mercado, irmão).

O "me liga quando estiver pronto" é a essência do código assíncrono. Em programação, o "telefone" é uma função que você entrega para ser chamada depois.

1. Código síncrono: o que você fez até agora

console.log("1. Liguei o forno");
console.log("2. Misturei a massa");
console.log("3. Coloquei o bolo no forno");
console.log("4. Lavei a louça");

$ node sincrono.js
1. Liguei o forno
2. Misturei a massa
3. Coloquei o bolo no forno
4. Lavei a louça

Nenhuma surpresa: as linhas rodam na ordem em que estão escritas, e cada uma só começa quando a anterior termina. Isso se chama síncrono ("ao mesmo tempo", "no compasso": tudo anda junto, em fila).

2. O primeiro código assíncrono: setTimeout

O setTimeout ("definir um tempo de espera") recebe uma função e um tempo em milissegundos (1000 ms = 1 segundo). Ele diz ao JavaScript: "daqui a esse tempo, chame esta função". E, sem esperar, o programa segue para a linha de baixo:

console.log("1. Encomendei o bolo na padaria");
setTimeout(() => {
  console.log("3. O bolo ficou pronto!");
}, 2000);
console.log("2. Enquanto isso, fui ao mercado");

A Ana rodou com o comando time na frente, que mede quanto tempo o programa levou:

$ time node primeiro.js
1. Encomendei o bolo na padaria
2. Enquanto isso, fui ao mercado
3. O bolo ficou pronto!

real	0m2,037s
user	0m0,024s
sys	0m0,012s
setTimeout(() => { … }, 2000)
Entrega a arrow function ao JavaScript, com o recado "chame daqui a 2000 ms". A função não roda agora: fica guardada.
"2. Enquanto isso…" saiu antes do "3"
O programa não ficou parado no setTimeout: foi direto para a linha 5. A ordem da saída (1, 2, 3) não é a ordem do código (1, 3, 2).
real 0m2,037s
O tempo total, no relógio: um pouco mais de 2 segundos. O Node esperou o timer antes de terminar: um programa só acaba quando não tem mais nada pendente.
user 0m0,024s
O tempo que o processador realmente trabalhou: 24 milésimos. Durante os 2 segundos de espera, o programa ficou parado sem gastar nada, só esperando o "telefone tocar". (Os números mudam um pouco de um computador para outro e de uma vez para outra.)

A função que você entrega para ser chamada depois tem um nome: callback ("chamar de volta"). O setTimeout e o seu irmão setInterval têm aula própria: setTimeout e setInterval.

Missão: do jeito que está, a Ana fica esperando o bolo antes de ir ao mercado. Coloque a linha do Bolo pronto! dentro de um setTimeout de 2000 ms, para a saída ficar: Encomendei o bolo., Enquanto isso, vou ao mercado. e, 2 segundos depois, Bolo pronto!.

console.log("Encomendei o bolo.");
console.log("Bolo pronto!");
console.log("Enquanto isso, vou ao mercado.");

console.log("Encomendei o bolo.");
setTimeout(() => {
  console.log("Bolo pronto!");
}, 2000);
console.log("Enquanto isso, vou ao mercado.");

E com 0 milissegundos?

Se o tempo for zero, a função roda na hora? Não:

console.log("A");
setTimeout(() => {
  console.log("B");
}, 0);
console.log("C");

$ node zero.js
A
C
B

O B saiu por último. Um callback nunca interrompe o código que está rodando: o JavaScript primeiro termina tudo o que está fazendo agora (o A e o C) e só depois olha a lista do que ficou pendente. O "0 ms" quer dizer "assim que você estiver livre", não "agora". É a regra mais importante do JavaScript assíncrono, e quem cuida dela é o Event Loop.

3. Uma pessoa só: o que trava o programa

O JavaScript (no Node e no navegador) faz uma coisa de cada vez: tem uma só "linha de execução" (em inglês, single thread). É como uma padaria com um só atendente. Ele consegue cuidar de muitas encomendas porque nunca fica parado esperando o forno. Mas, se ele começar uma tarefa trabalhosa (contar um saco de moedas, por exemplo), ninguém mais é atendido até ele acabar, nem o cliente cujo bolo já está pronto.

setTimeout(() => {
  console.log("O timer de 0 ms finalmente rodou");
}, 0);

console.log("Começando uma conta enorme...");
let soma = 0;
for (let i = 0; i < 2_000_000_000; i++) {
  soma = soma + i;
}
console.log("Terminei a conta");

$ time node bloqueio.js
Começando uma conta enorme...
Terminei a conta
O timer de 0 ms finalmente rodou

real	0m2,921s
user	0m2,914s
sys	0m0,008s

O timer pediu "0 ms", mas só rodou depois de quase 3 segundos: o for de 2 bilhões de voltas (o 2_000_000_000 é só o número 2000000000 com separadores, para ler melhor) ocupou o atendente o tempo todo. Desta vez, o user ficou quase igual ao real: o processador trabalhou sem parar.

Tipo de demoraExemploTrava o programa?
Esperar algo de foraTimer, ler arquivo, internet, clique do usuárioNão, se for feita do jeito assíncrono: o JavaScript pede e segue
Calcular muitoUm laço de bilhões de voltasSim: o atendente está ocupado de verdade

No navegador, travar é ainda pior: enquanto o JavaScript está ocupado, a página congela: os botões não respondem, o texto não rola. É por isso que tudo o que espera algo de fora, no JavaScript, é assíncrono.

4. Um exemplo de verdade: ler um arquivo

Esperar um timer é um exemplo de brinquedo. A demora de verdade é ler o disco, a rede, o banco de dados. A Ana tem um arquivo cardapio.txt na pasta dela:

$ cat cardapio.txt
Pão francês
Pão de queijo
Bolo de cenoura

O módulo fs do Node (aula Lendo Arquivos) tem os dois jeitos de ler. O síncrono, com Sync no nome, espera o arquivo chegar:

const fs = require("node:fs");

console.log("Vou ler o cardápio...");
const texto = fs.readFileSync("cardapio.txt", "utf8");
console.log(texto);
console.log("Pronto, li.");

$ node ler-sync.js
Vou ler o cardápio...
Pão francês
Pão de queijo
Bolo de cenoura

Pronto, li.

Na ordem do código, como sempre. (A linha em branco é a quebra de linha que já existia no fim do arquivo, mais a do console.log.) Agora o assíncrono, sem o Sync, que recebe um callback:

const fs = require("node:fs");

console.log("Vou ler o cardápio...");
fs.readFile("cardapio.txt", "utf8", (erro, texto) => {
  console.log(texto);
});
console.log("Pedi o arquivo e segui em frente.");

$ node ler-async.js
Vou ler o cardápio...
Pedi o arquivo e segui em frente.
Pão francês
Pão de queijo
Bolo de cenoura
fs.readFile("cardapio.txt", "utf8", callback)
"Leia este arquivo, como texto (utf8), e, quando terminar, chame esta função." O Node passa o pedido para o sistema operacional e volta na hora.
(erro, texto) => { … }
O callback recebe dois valores: um erro (se algo deu errado, como o arquivo não existir) e o conteúdo. Essa ordem, erro primeiro, é um padrão do Node que a aula Callbacks Assíncronos explica.
"Pedi o arquivo e segui em frente." antes do cardápio
A mesma inversão do setTimeout: o programa não esperou o disco.

Num programa pequeno como este, tanto faz. Mas num servidor que atende mil pessoas ao mesmo tempo, o readFileSync faria todas esperarem cada leitura de disco; o readFile deixa o Node atender outras pessoas enquanto o disco trabalha. Foi essa ideia que tornou o Node famoso.

Três jeitos de escrever código assíncrono

O JavaScript ganhou, ao longo dos anos, três estilos para dizer "faça isto quando aquilo terminar". Você vai aprender cada um nas próximas aulas; por enquanto, só reconheça. Os três leem o mesmo cardápio e mostram a primeira linha:

const fs = require("node:fs");
const fsp = require("node:fs/promises");

// 1. callback: entrego uma função para ser chamada depois
fs.readFile("cardapio.txt", "utf8", (erro, texto) => {
  console.log("callback:", texto.split("\n")[0]);
});

// 2. Promise: recebo um "vale" e digo o que fazer quando ele for pago (.then)
fsp.readFile("cardapio.txt", "utf8").then((texto) => {
  console.log("then:", texto.split("\n")[0]);
});

// 3. async/await: escrevo como se fosse síncrono, e o await espera sem travar
async function ler() {
  const texto = await fsp.readFile("cardapio.txt", "utf8");
  console.log("await:", texto.split("\n")[0]);
}
ler();

$ node tres-jeitos.js
callback: Pão francês
then: Pão francês
await: Pão francês

(As três leituras correm ao mesmo tempo, então a ordem das três linhas não é garantida: quem terminar primeiro escreve primeiro.)

EstiloDesdeComo éAula
CallbackSempre existiuVocê entrega uma função; ela é chamada no fimCallbacks Assíncronos
PromiseES2015A operação devolve um objeto "promessa"; você encadeia .then e .catchPromises
async/awaitES2017Parece código comum, linha a linha; por baixo, são Promisesasync e await

Em código novo, o mais usado é o async/await. Mas ele é construído em cima das Promises, que por sua vez resolvem problemas dos callbacks; por isso o guia ensina nessa ordem.

Quando dá errado

Os erros do código assíncrono quase nunca são erros de escrita: o programa roda, mas faz as coisas na ordem que você não esperava.

Usou o resultado antes de ele chegar 
const fs = require("node:fs");

let cardapio;
fs.readFile("cardapio.txt", "utf8", (erro, texto) => {
  cardapio = texto;
});
console.log(cardapio);

$ node cedo.js
undefined

O erro mais comum de todos. A Ana guardou o texto numa variável de fora e a mostrou na linha 7. Mas a linha 7 roda logo depois do pedido, muito antes de o disco responder: nesse momento, o callback ainda não rodou e cardapio continua undefined (aula null e undefined). É a Ana tentando cortar o bolo no instante em que fez a encomenda. Como consertar: tudo o que depende do resultado vai dentro do callback (ou depois de um await, que você vai aprender em breve).

Tentou devolver (return) o resultado de dentro do callback 
const fs = require("node:fs");

function lerCardapio() {
  fs.readFile("cardapio.txt", "utf8", (erro, texto) => {
    return texto;
  });
}

const cardapio = lerCardapio();
console.log(cardapio);

$ node retorno.js
undefined

O return texto devolve o texto para quem chamou o callback (o próprio Node, que ignora), e não para quem chamou lerCardapio. E a lerCardapio termina na hora, sem return nenhum, devolvendo undefined (aula return). Como consertar: uma função que depende de algo assíncrono não consegue devolver o resultado pronto. Ela devolve uma Promise (o "vale" do bolo), e quem chama espera por ela: é o assunto de Promises e async e await.

Mostrou a Promise em vez do conteúdo 
const fsp = require("node:fs/promises");

const cardapio = fsp.readFile("cardapio.txt", "utf8");
console.log(cardapio);

$ node promessa.js
Promise { <pending> }

"Promessa (pendente)". A versão fs/promises não recebe callback: devolve na hora uma Promise, o "vale" de um resultado que ainda vai chegar. <pending> quer dizer que ele ainda não chegou. É a Ana mostrando o papel da encomenda em vez do bolo. Como consertar: .then(...) ou await, como no exemplo dos três jeitos. Sempre que vir Promise { <pending> } na saída, faltou esperar.

O try … catch não pegou o erro 
try {
  setTimeout(() => {
    throw new Error("o forno queimou o bolo");
  }, 100);
} catch (erro) {
  console.log("Peguei o erro:", erro.message);
}
console.log("Fim do try");

$ node trycatch.js
Fim do try
/home/ana/trycatch.js:3
    throw new Error("o forno queimou o bolo");
    ^

Error: o forno queimou o bolo
    at Timeout._onTimeout (/home/ana/trycatch.js:3:11)
    at listOnTimeout (node:internal/timers:685:17)
    at process.processTimers (node:internal/timers:618:7)

Node.js v24.22.0

O try (aula try … catch) só protege o que roda enquanto ele está aberto. Ele agendou o timer e terminou na hora (Fim do try aparece primeiro). 100 ms depois, o callback rodou e lançou o erro, mas o try já tinha acabado fazia tempo: ninguém pegou, e o Node parou o programa. Repare na pilha: at Timeout._onTimeout e at listOnTimeout (node:internal/timers…) dizem que quem chamou a função foi o sistema de timers do Node, e não o seu código. Como consertar: o try … catch vai dentro do callback. Com Promises e await, os erros voltam a ser pegos de um jeito natural (aulas seguintes).

Missão: este programa mostra Cardápio de hoje: e undefined, porque usa o texto antes de ele chegar. Mova as duas linhas de console.log para dentro do callback (e mostre texto em vez de cardapio), para aparecer o cardápio de verdade. O arquivo cardapio.txt está na outra aba.

const fs = require("node:fs");

  cardapio = texto;

Resumo

  • Síncrono: cada linha espera a anterior. Assíncrono: começa uma tarefa demorada, segue em frente e reage quando ela termina, por meio de uma função entregue para depois (o callback).
  • Com código assíncrono, a ordem da saída pode não ser a ordem do código. Um callback nunca interrompe o código que está rodando, nem com setTimeout de 0 ms.
  • O JavaScript faz uma coisa de cada vez. Esperar (timer, disco, rede, clique) não trava, se for assíncrono; calcular muito trava tudo, inclusive a página no navegador.
  • O Node só termina o programa quando não há mais nada pendente (timers, leituras).
  • Há três estilos: callbacks, Promises e async/await, que você vai aprender nessa ordem.
  • Use o resultado dentro do callback (ou depois do await): fora dele, ainda é undefined.
