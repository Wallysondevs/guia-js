JavaScript O Event Loop

Nas últimas aulas, você viu o JavaScript "esperar" um timer, uma Promise, várias Promises juntas, e mesmo assim continuar rodando outras linhas enquanto espera. Como ele faz isso? O JavaScript tem uma mão só: executa uma coisa por vez. O truque está num mecanismo chamado event loop ("laço de eventos"), que decide o que roda depois. Entender o event loop explica todas as ordens "estranhas" de saída que você já viu, e evita alguns erros feios.

Você vai aprender
  • Por que o JavaScript faz uma coisa por vez, e o que é a pilha de chamadas.
  • O que é a fila de tarefas, e por que um setTimeout de 0 ms roda depois do resto do código.
  • O que é a fila de microtarefas (.then, await, queueMicrotask) e por que ela passa na frente dos timers.
  • O process.nextTick, que existe só no Node.
  • Por que um cálculo pesado atrasa os timers (e trava a página no navegador).
  • O erro clássico do laço que espera uma variável mudar e nunca termina, e como consertar.

Os programas desta aula rodaram no Node.js 24 da máquina da Ana (usuária ana, computador notebook) com node arquivo.js. O event loop do navegador funciona do mesmo jeito nas partes que esta aula mostra; as diferenças estão marcadas.

A ideia: a cozinheira que faz uma coisa por vez

Imagine a cozinha da padaria com uma cozinheira só. Ela tem:

  • a tarefa que está fazendo agora (com as mãos ocupadas, não larga no meio);
  • um espeto de comandas: os pedidos novos ficam espetados ali, em fila, na ordem em que chegaram;
  • um bloquinho de "coisas rápidas": lembretes curtos do tipo "assim que terminar isso, tempere o molho".

E o forno, o timer da cozinha e o telefone trabalham sozinhos: quando o timer apita, ninguém interrompe a cozinheira; uma comanda nova é espetada na fila.

A rotina dela é sempre a mesma, para sempre:

  1. Termina a tarefa que está fazendo, até o fim.
  2. Faz todos os lembretes do bloquinho de coisas rápidas.
  3. Pega a próxima comanda do espeto e volta ao passo 1.

Essa rotina é o event loop. No JavaScript:

Na cozinhaNo JavaScript
A cozinheira (uma só)O JavaScript, que roda uma coisa por vez (dizem que ele é single-threaded, "de um fio só")
A tarefa que ela está fazendo agoraA pilha de chamadas (call stack): o código rodando agora
O espeto de comandasA fila de tarefas (task queue): timers que venceram, cliques, dados que chegaram
O bloquinho de coisas rápidasA fila de microtarefas (microtask queue): o .then das Promises e a continuação depois de um await
O forno, o timer, o telefoneO Node ou o navegador, que contam o tempo, leem arquivos e buscam dados fora do JavaScript

1. A pilha de chamadas: uma coisa de cada vez

O código comum, síncrono (sem timers nem Promises), roda de cima para baixo. Quando uma função chama outra, a de fora espera a de dentro terminar:

function picarCebola() {
  console.log("picando a cebola");
}

function fazerMolho() {
  console.log("começando o molho");
  picarCebola();
  console.log("molho pronto");
}

console.log("abrindo a cozinha");
fazerMolho();
console.log("fechando a cozinha");

$ node pilha.js
abrindo a cozinha
começando o molho
picando a cebola
molho pronto
fechando a cozinha

Pense numa pilha de pratos. Quando o programa chama fazerMolho(), ela vai para o topo da pilha; quando fazerMolho chama picarCebola(), essa vai por cima. A de cima tem de terminar e sair da pilha para a de baixo continuar. Quando a pilha fica vazia, o código síncrono acabou. É só nesse momento que o event loop olha as filas. (As linhas at … das mensagens de erro do Node são justamente essa pilha, impressa de cima para baixo: veja Lendo uma Mensagem de Erro.)

2. A fila de tarefas: por que o setTimeout de 0 ms espera

Na aula setTimeout e setInterval, o setTimeout pedia para rodar uma função "daqui a tantos milissegundos". E com 0?

console.log("1. Anotei o pedido");
setTimeout(() => {
  console.log("3. Timer: tirar o bolo do forno");
}, 0);
console.log("2. Lavei a louça");

$ node timeout0.js
1. Anotei o pedido
2. Lavei a louça
3. Timer: tirar o bolo do forno

Mesmo com 0 ms, o timer rodou por último. O que aconteceu, passo a passo:

  1. A linha 1 mostra 1. Anotei o pedido.
  2. O setTimeout entrega a função para o Node ("o timer da cozinha") e segue na hora, sem rodá-la.
  3. O tempo de 0 ms vence logo, e a função vai para o fim da fila de tarefas (uma comanda espetada).
  4. Mas a cozinheira ainda está ocupada: a linha 5 mostra 2. Lavei a louça.
  5. O código síncrono acabou, a pilha esvaziou. O event loop pega a próxima tarefa da fila: o timer. Aparece o 3.

Ou seja, o número do setTimeout é o tempo mínimo de espera, nunca uma garantia de "rodar exatamente agora". Uma tarefa da fila só roda quando a pilha está vazia.

Vários timers saem na ordem em que vencem, não na ordem em que foram escritos:

setTimeout(() => console.log("timer de 200 ms"), 200);
setTimeout(() => console.log("timer de 0 ms"), 0);
setTimeout(() => console.log("timer de 100 ms"), 100);
console.log("fim do código síncrono");

$ node dois-timers.js
fim do código síncrono
timer de 0 ms
timer de 100 ms
timer de 200 ms

Missão: sem mudar a ordem das linhas, faça o Pedido 2 aparecer por último. Dica: embrulhe o console.log("Pedido 2") num setTimeout(() => …, 0).

console.log("Pedido 1");
console.log("Pedido 2");
console.log("Pedido 3");

console.log("Pedido 3");

3. A fila de microtarefas: o .then passa na frente

As Promises não usam a fila de tarefas: elas têm uma fila só delas, a de microtarefas (o bloquinho de coisas rápidas). A regra que decide tudo: depois de cada tarefa, o event loop esvazia a fila de microtarefas inteira, e só então pega a próxima tarefa. Por isso uma microtarefa sempre passa na frente de um timer, mesmo de 0 ms.

O queueMicrotask(função) ("enfileirar microtarefa") põe uma função diretamente nessa fila. Veja os três juntos:

console.log("1. síncrono: começo");

setTimeout(() => console.log("5. timer (setTimeout 0)"), 0);

Promise.resolve().then(() => console.log("3. microtarefa (then)"));

queueMicrotask(() => console.log("4. microtarefa (queueMicrotask)"));

console.log("2. síncrono: fim");

$ node ordem.js
1. síncrono: começo
2. síncrono: fim
3. microtarefa (then)
4. microtarefa (queueMicrotask)
5. timer (setTimeout 0)
OrdemPor quê
1 e 2Código síncrono: roda primeiro, inteiro, de cima para baixo
3 e 4Microtarefas: rodam assim que a pilha esvazia, na ordem em que entraram na fila
5Tarefa (timer): só depois que a fila de microtarefas ficou vazia

Promise.resolve() cria uma Promise já resolvida (veja Promises), e mesmo assim o .then não roda na hora: a função dele sempre vai para a fila de microtarefas. Um .then nunca roda no meio do seu código síncrono.

E o await?

O await é feito de Promises, então segue a mesma regra. Tudo o que vem depois de um await é uma microtarefa: a função pausa, o código de quem a chamou continua, e a função volta pela fila de microtarefas:

async function preparar() {
  console.log("B. preparar: antes do await");
  await null;
  console.log("D. preparar: depois do await");
}

console.log("A. início");
preparar();
console.log("C. fim do código síncrono");

$ node await-ordem.js
A. início
B. preparar: antes do await
C. fim do código síncrono
D. preparar: depois do await

Repare no B: o começo de uma função async, até o primeiro await, roda na hora, como código comum. Só o que vem depois do await espera, mesmo que seja um await null, que não tem nada para esperar. É o mesmo padrão que você viu em async e await, na padaria que não para.

Só no Node: process.nextTick

O Node tem uma fila ainda mais apressada, a do process.nextTick(função) ("no próximo tique"), que roda antes até das microtarefas das Promises. Ela não existe no navegador:

setTimeout(() => console.log("4. setTimeout"), 0);
Promise.resolve().then(() => console.log("3. then"));
process.nextTick(() => console.log("2. nextTick"));
console.log("1. síncrono");

$ node nexttick.js
1. síncrono
2. nextTick
3. then
4. setTimeout

No seu código, você quase nunca vai precisar dele; ele aparece em bibliotecas do Node. Em código novo, prefira queueMicrotask, que funciona no Node e no navegador (é o que a documentação do Node recomenda).

4. Quem trava a cozinha trava tudo

A cozinheira não larga uma tarefa no meio. Se ela começa algo que demora 2 segundos, nenhuma comanda é atendida nesses 2 segundos, nem os timers. Veja um timer de 100 ms disputando com um cálculo que ocupa o JavaScript por uns 2 segundos (o while só fica repetindo até o relógio passar de 2000 ms; veja Datas para o Date.now()):

const inicio = Date.now();

setTimeout(() => {
  console.log(`O timer de 100 ms rodou depois de ${Date.now() - inicio} ms`);
}, 100);

// um cálculo pesado, que ocupa a cozinheira por uns 2 segundos
let soma = 0;
while (Date.now() - inicio < 2000) {
  soma++;
}
console.log("Cálculo pesado terminou");

$ node bloqueio.js
Cálculo pesado terminou
O timer de 100 ms rodou depois de 2004 ms
$ node bloqueio.js
Cálculo pesado terminou
O timer de 100 ms rodou depois de 2005 ms

O timer pediu 100 ms e esperou mais de 2000. Aos 100 ms, a função dele foi para a fila, mas a pilha estava ocupada com o while; o event loop só conseguiu pegá-la quando o cálculo acabou. (Os números mudam um pouco a cada execução: 2004, 2005…)

No navegador, a página congela

No navegador, o mesmo event loop cuida dos cliques, da digitação e de redesenhar a tela. Um código que ocupa o JavaScript por 3 segundos deixa a página congelada por 3 segundos: os botões não respondem, o texto não aparece. Experimente abaixo: clique em Contar algumas vezes, depois em Travar 3 s, e logo em seguida em Contar de novo.

Experimente: enquanto o "Travar 3 s" roda, os cliques em "Contar" ficam na fila. Quando o laço termina, eles são atendidos todos de uma vez.

<button id="contar">Contar</button>

<p>Cliques: <span id="total">0</span></p>

Os botões e o addEventListener são assunto do grupo A Página Web; aqui basta ver o efeito. A lição vale para o Node e para o navegador: não ocupe o JavaScript por muito tempo de uma vez. Se um trabalho é longo, divida-o em pedaços e deixe o event loop respirar entre eles.

Dividir em pedaços

Um await de um timer de 0 ms entre os pedaços devolve a vez ao event loop: o que estava na fila consegue rodar.

function esperar(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

setTimeout(() => console.log("  (o timer conseguiu rodar no meio)"), 0);

for (let parte = 1; parte <= 3; parte++) {
  console.log(`Processando a parte ${parte}`);
  await esperar(0);
}
console.log("Tudo processado");

$ node fatias.js
Processando a parte 1
  (o timer conseguiu rodar no meio)
Processando a parte 2
Processando a parte 3
Tudo processado

Depois da parte 1, o await esperar(0) pausou o laço e pôs um timer na fila, atrás do timer que já estava lá. O event loop atendeu o da frente (a mensagem do meio) e só depois voltou ao laço.

Resumo das filas: quem roda primeiro

OrdemO quêExemplos
1ºCódigo síncrono (a pilha, até esvaziar)as linhas do arquivo, funções comuns, o começo de uma função async até o primeiro await
2ºSó no Node: a fila do nextTickprocess.nextTick(f)
3ºMicrotarefas (todas, até a fila esvaziar).then, .catch, .finally, o que vem depois de um await, queueMicrotask(f)
4ºUma tarefa, e de novo o 2º e o 3ºsetTimeout, setInterval, cliques e teclas (navegador), arquivos lidos e dados que chegaram (Node)

O Node divide a fila de tarefas em fases (timers, entrada e saída, setImmediate…), e o navegador tem as dele (como redesenhar a tela). Para quem está começando, a tabela acima basta; os detalhes estão na documentação do Node, no guia The Node.js Event Loop.

Quando dá errado

Esperar uma variável mudar com um laço: o programa nunca termina 
let pronto = false;

setTimeout(() => {
  pronto = true;
}, 1000);

while (!pronto) {
  // esperando o bolo ficar pronto...
}
console.log("Bolo pronto!");

$ timeout 3 node esperaflag.js
$ echo $?
124

A ideia parece boa: "fique repetindo até o pronto virar true". Mas a função que muda o pronto é uma tarefa da fila, e ela só roda quando a pilha esvaziar. A pilha nunca esvazia, porque o while não termina. A cozinheira fica olhando para o forno sem parar, e por isso nunca ouve o timer. Um laço infinito sem nenhuma mensagem.

A Ana rodou com o comando timeout 3 do Linux, que mata o programa depois de 3 segundos. O echo $? mostra o código de saída: 124 é o jeito do timeout dizer "precisei matar". Sem o timeout, o programa ficaria rodando até você apertar Ctrl+C.

Como consertar: dentro do laço, devolva a vez ao event loop com um await:

function esperar(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

let pronto = false;

setTimeout(() => {
  pronto = true;
}, 1000);

while (!pronto) {
  await esperar(100);
}
console.log("Bolo pronto!");

$ node esperaflag-ok.js
Bolo pronto!

Melhor ainda: em vez de ficar perguntando, faça o próprio timer resolver uma Promise e dê await nela, como em async e await.

Achar que o setTimeout(…, 0) roda na hora 
let nome;
setTimeout(() => {
  nome = "Ana";
}, 0);
console.log(`Olá, ${nome}!`);

$ node cedo.js
Olá, undefined!

O console.log é síncrono e roda antes do timer, quando nome ainda não tem valor (undefined; veja null e undefined). Como consertar: use o valor dentro da função do timer, ou espere o timer com await.

Um cálculo longo atrasa os timers

Não aparece erro nenhum: só atraso, como em bloqueio.js (o timer de 100 ms rodou depois de 2004 ms). No navegador, o sintoma é a página que não responde aos cliques e, se demorar muito, o aviso de "página sem resposta" do navegador. Como consertar: divida o trabalho em pedaços com await esperar(0), como em fatias.js.

Resumo

  • O JavaScript faz uma coisa por vez: o código síncrono roda inteiro, de cima para baixo, na pilha de chamadas.
  • Timers, cliques e dados que chegam viram tarefas numa fila; uma tarefa só roda quando a pilha está vazia. Por isso setTimeout(f, 0) roda depois.
  • .then, o que vem depois de um await e queueMicrotask são microtarefas: rodam todas antes da próxima tarefa.
  • Ordem: síncrono → (nextTick, só no Node) → microtarefas → uma tarefa → microtarefas → …
  • Um cálculo longo atrasa timers e congela a página; um while esperando uma variável que um timer mudaria nunca termina. Devolva a vez com await.
